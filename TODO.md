### Speed (Lighthouse, 2026-11-07)

Measured on loopworkouts.com with Lighthouse 12.8, the middle of three runs, on its test phone (slow 4G, CPU slowed 4×). Mobile performance: Welcome 89 (desktop 98), Today 81, Workouts 88, Exercises 97, Progress 88, an exercise's page (push-up) 59. Accessibility and best practices 100, SEO 92. To measure again, Lighthouse a production build or the live site, as a guest already welcomed (`welcomed` set to `guest`), and compare total blocking time, as it's what most of these change; the lab can't stand in for real phones, so for those, see Vercel Speed Insights below.

- [x] **The 3D demo held up an exercise's page** (2026-11-07): building the figure, painting it, sending it to the GPU and its first frame were one task of about 2.1s on the test phone. They're steps of their own now, after the page has shown (`prepareScene()` in `figure-scene.ts`), and it's painted once rather than twice. Measured in the browser with the CPU slowed 4×, the worst freeze went from about 640ms to 400ms and the blocking from about 1s to 0.8s; Lighthouse's score hardly moves, as each step is still over 50ms. To get it under that:
    - [x] **Draw it in a worker** (2026-11-07): `figure.worker.ts` builds, paints and draws the figure on an `OffscreenCanvas`, and the page copies each picture onto its canvas; on the page as above where the browser can't (Safari before 17, say). In the browser with the CPU slowed 4×, the page's blocking went from about 850ms to 50–120ms, and Lighthouse's score for the push-up page from about 56 to 84 (both measured on a local production build). The worker brings its own copy of the body map's drawings (`body-shapes.ts`), which the page loads too for its body map, so an exercise page downloads about 30–45 KiB more than before.
    - [x] **Keep the built body between exercises** (2026-11-07): `sharedBody()` in `figure-body.ts` builds each figure's body once and keeps it, and each exercise's `FigureScene` uses its parts, copying only the torso, which it reshapes for each pose. Shared parts aren't disposed of with a scene. In the test browser, the first figure took 53ms to make and the ones after 1–5ms; with the CPU slowed 4× that's about the 270ms saved for each exercise opened after the first.
    - **A smaller painting,** 1024 rather than 2048 square, would paint and upload in about a quarter of the time. It changes how sharp the muscles are, so for Dan to look at first.
- [x] **A `robots.txt`** (2026-11-07): there wasn't one, so the app's page came back in its place, failing Lighthouse's SEO check (92). `public/robots.txt` allows everything.
- [x] **Only the icons the app uses** (2026-11-07): the Material Icons font (126 KiB, the biggest file on every page) is now Material Symbols with only the 50 icons the app uses (`icon_names=` in `index.html`), about 7 KB with the fill axis. They're filled, as before; `icon-outline` draws one as an outline (a favourite's heart when off, and the ⓘ, ? and ⊕ that were `_outline` names). `npm run lint` runs `tools/check-icons.mjs`, which fails if an icon used isn't in the list or one listed isn't used. Most look the same; the You tab's `account_circle` is a face in a ring rather than a solid disc, and `content_copy` and `delete` are a little heavier.
- [x] **The body map only where it shows** (2026-11-07): its drawings (`body-shapes.ts`, 58 KiB) loaded with Today and Progress, even for a new guest with nothing to show on them. Muscles this week now loads it itself once there's something to show on it, its space kept the same size till then. Not with `@defer`, which brought 8 kB of Angular into the first load, for every page. The Exercises list's map is near the top of its page, so it loads as before. Measured locally, Today went from 406 to 351 KiB for a new guest.
- [x] **Supabase only when signing in** (2026-11-07): the welcome page loaded the whole Supabase client (59 KiB) as it opened, as `AccountService` started it at once. It starts at once now only on a device with a session saved or a sign-in coming back in the address; otherwise once the sign-in form is used. Measured locally, Welcome went from 406 to 352 KiB, and its largest paint about 0.4s sooner on the test phone.
- [x] **Today's chain of files** (2026-11-07): its slowest path was five requests, each found only once the one before had loaded (the page, `main`, Today's chunk, then what that imports). `npm run build` now runs `tools/preload-today.mjs` after `ng build`, which adds a small script to the built `index.html` that preloads Today's chunk and the 12 it imports (80 kB) when the page opens on `/` or `/home`, and adds the script's hash to the Content-Security-Policy. It finds the chunks in the build's `browser-stats.json` (`statsJson` in `angular.json`), and `vercel.json` sets the build command to `npm run build` so Vercel runs it too. Measured on a local production build with slow 4G and the CPU slowed 4×, Today's largest paint went from about 4.2s to 3.7s. Preloading on every page instead made the Exercises list's about 0.45s later, so it's left to Today.
